# 03: Matching

Status: claimed
Blocked by: 02 (Let one question box hold several questions)

Spec: [Content types](../spec.md) › Behaviour: the matching (Writing one, How it looks, Checking), Documentation and Shared parts. Its explanation is 05; the source position of an item ID's failure is 04.

**What to build:** an agent imports `Matching` from the design system and writes a prompt, the options as one numbered list, `---` between blank lines, then the items as one bulleted list, with `answers={{ "<item-id>": n }}` in the items' order. The owner sees one question box headed "Questões 3–5" / "Questions 3–5" with the hint "Associe" / "Match": the prompt, the options once, lettered a), b), c) by the page, then one row per item with its own question number, its text and a row of letter choices. Once every unanswered item has a choice, one Check saves them all, and each item locks with its own mark: a tick when right; on a wrong one, its chosen letter crossed out and the right one ticked. The items are ordinary questions everywhere else: the stopping point, Next question, the attempts panel and the Library's to-revisit list go to an item's row and name it "Questão 4", and the next question after the set continues the series.

A matching is several **auto-checked questions** (`GLOSSARY.md` › Matching): each item is recorded on the page, in the questions block and in the question manifest as a single-choice question with its own ID and key, so its response is the chosen option's number, right when it equals the key. Artifact state, the Worker and the scoring module don't change ([ADR 0001](../../../docs/adr/0001-artifact-state-stores-answers-only.md)), and the scoring seam gets no new test. CSS counters can't print a range ahead of the rows they count; the build already knows each question's number, so the range can be written at build time, as the frame writes a statement's number.

This is design-system work: do it in a local session, through impeccable (`design-system/CLAUDE.md`).

**The set's status:** while any item is saving, not saved, answered elsewhere or signed out, the header's status is the one a question box shows for that state, taken from the most urgent of its items (not saved or signed out, then saving, then answered elsewhere). "Try saving again" retries every unsaved item. Once every item locks, the header says only that the set is answered, and each item carries its own right or wrong mark. No score shows anywhere (`DESIGN.md`): no count such as "2 de 3 corretas", on screen or in print. While a reopened set has an unanswered item, the header shows the hint.

- [ ] Written as the spec shows, a matching builds; any option may be right for any number of items, or for none. The build fails with a component error naming `Matching` when the number of `answers` differs from the number of items, with fewer than two items or two options, when an answer names no option, when an option or item isn't one paragraph of inline content, and when anything follows the items list (05 lets an explanation follow it). Each failure is tested at the `pnpm check` seam.

## Comments

### 2026-11-09: from 02

Implementer of [02](02-question-box-holds-several-questions.md#comments). The split you build on:

- **The box** is `QuestionBox` in `design-system/src/question-element.ts`: the form, Check, `.question-status` and `.question-recovery`, the store subscription and the inert start. A matching's element extends it and sets `protected readonly answers` to one `QuestionAnswer` per item. `QuestionElement` (the three kinds) is the one-question box: `answers = [new QuestionAnswer(this, this)]`.
- **Each item's answer** is a `QuestionAnswer` (`design-system/src/question-answer.ts`), given the row that carries the item's markers and a `{ readResponse, showResponse }` for that row. It names the row "Questão N" (`aria-label`), saves it, shows its response, disables the `fieldset`s inside the row and sets the row's `data-status` and `data-mark`, and reopens it. `querySelectorAll` doesn't include the row itself, so give each row its own inner `fieldset` (a row that is itself the `fieldset` won't lock).
- **Check** is already the set's: it is enabled once every answer without a `data-status` has a response, and pressing it saves every unanswered answer only when each has one. A reopen resets the whole form once, then the locked answers show their responses again, so an added item opens alone.
- **What 03 replaces:** `QuestionBox`'s `#show` reports only the first shown answer (`const [shown] = …`), which is all one question needs. Replace that with the set's rule (most urgent item, then "answered"), and set the box's own `data-status`/`data-mark` from it: `Question.astro`'s outline and header sign key on `.question[data-status]` and `> form > .question-header`, and with the markers on the rows nothing sets them on the box. `wrongAnswerLocked` reads the one-question box's dataset; an item's right-letter tick needs the row's.
- **Unchanged and still yours:** `Question.astro` always puts the markers on the box, and `question-markers.ts`'s regex reads any start tag whose attributes open `id="q-…" data-question-id=… data-question-kind=…` in that order. So a matching box must render without markers, each row must render them first and in that order, and the frame's `.question` counter (`ArtifactFrame.astro`) counts boxes, not items.
