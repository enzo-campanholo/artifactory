# Custom builds

The rules for a `Stage`'s `<build>.build.ts`, after the [Custom builds](rules.md#custom-builds) section's first three, then what [Look](SKILL.md#look) shoots of a Stage.

- **Imports:** only `@artifactory/design-system/stage-build` and the machines under `@artifactory/design-system/machines/` (`@artifactory/design-system/machines/mepa`). Failure: "`x` isn't `@artifactory/design-system/stage-build` or a machine under `@artifactory/design-system/machines/`, the only modules a build may import", at the import.
- **A machine the design system holds is traced, never copied:** a Stage that steps through a program on a machine such as MEPA has the build `export default trace(mepa, { reads: ["x", "y"], … })`, importing `trace` from `stage-build` and the machine from `machines/`, and nothing else. Write the program once, in the Stage's code block, and the machine's tables as its entry under `COMPONENTS.md`'s Machines shows them, in the artifact's main language; the machine says every step in that language. `reads` names exactly the Stage's fields, in the order the machine reads them, or the build fails as `build-input`: "`steps` takes `{ a: number }`, but the Stage's fields give it `{ a: number; b: number }`: name exactly the Stage's fields in `reads`". The rest of the notes are keyed by address or label (MEPA's `roles` and `after` by address, its `labels` by label), in the artifact's language, never taken from the code's `;` comments. Every cell whose text changes since the step before is `strong`. The tables as written are still the first example's last step, and runs stay under 200 steps, so bound the fields. A run that faults fails, and the page refuses it with the line and the fault ("Linha 8: divisão por zero."): "with `x = 7, y = 0`, the machine faults at line 8: division by zero" (each machine's entry lists its faults). A program or notes that don't fit the machine fail as `stage-run` too, every problem named once, with the first example, and the page refuses them with its "couldn't be worked out" line: a code line by its shown number, "with `x = 7, y = 2`, the machine can't read line 1: `PUSH 3` isn't a MEPA instruction" or "… line 1: `DSVS L9` jumps to the label `L9`, which the listing doesn't have: it has `L1`", or a note, "the machine can't run: `roles` names the address 7, which the listing doesn't have: it has addresses 0 to 2", "the machine can't run: `labels` names the label `L2`, which the listing doesn't have: it has `L1`", and "the machine can't run: `reads` names `z`, which isn't one of the Stage's fields". A table, column or row the machine writes into that the content lacks fails as any Stage's does, once per run: "step 1 changes a cell in the column `Value`, which heads no table".
- **Types:** builds are strict TypeScript with the ES library only, so no DOM or Node: `document`, `window`, `fetch`, `localStorage`, `process` and `console` fail as `TS…` at the name ("Cannot find name 'document'"). A build turns a choice into data and touches nothing else.
- **Typed input:** give `defineBuild` one object type with exactly the Stage's field names, each required: a number field's a `number`, a text field's a `string`, so `steps` gets them typed. A mismatch fails as `build-input` at the type: "`steps` takes `{ a: number; c: number }`, but the Stage's fields give it `{ a: number; b: number }`: write `defineBuild<{ a: number; b: number }>`", "`steps` takes `{ w: number }`, but the Stage's fields give it `{ w: string }`: write `defineBuild<{ w: string }>`", or, for a typed build behind `choose`, "… but the Stage's options give it text: write `defineBuild` without a type".
- **Text fields:** a field with `kind: "text"`, `{ name, label?, kind: "text", alphabet?, minLength?, maxLength }`, takes a word over `alphabet` (symbols of one code point each) or, without it, one line of any text, at most `maxLength` symbols and at least `minLength` (0 if left out, so the empty word counts). A field without `kind` stays a whole number, and one Stage may mix both, such as a hash's `{ t: string; m: number }`. `steps` gets the text in NFC, untrimmed and with its case kept, `""` for the empty word: walk and count it by code point, `[...w]`. Write the examples in NFC. A multi-character symbol, such as a parser's `id`, is the build's to split: give the field no alphabet and tokenise in the build. Print and the page without JavaScript name the first example's text bare in the code face, `ε` for the empty word ("Aceita w? w = aabba"). When the symbols matter, `say` spells them out ("lê a, a, b, b, a") and says "a palavra vazia", never "ε", since a screen reader reads `aabba` as one word.
- **The content as written is `steps`'s second argument,** typed `Content`, so a program or a table's starting values are written once, in the content, and read from there: `code`, each code block's lines in order as `{ line, text }`, `line` the number the page shows (0 first under `start=0`) and `text` the line's plain text; `tables`, each table's `columns` (header texts) and `rows` as written, plain text found as `rows` and `cells` find them, even in a run that gives `body`; and `lang`, the artifact's main language, `"pt-BR"` or `"en"`, to say the steps in. `steps({ a, b }, { code: [listing = []], lang })` takes the first block's lines. The page and the check hand every run the same content, a fresh copy each time. A build that doesn't need it leaves the argument out.
- **With `input`, the content as written is the first example's result.** Write each table as the first example's last step leaves it, or the run fails: "with `a = 48, b = 18`, the first example, the last step leaves `0` in the row `b` and the column `Valor`, and the table as written has `12`; write the tables as the first example leaves them", with a line of its own for a row the last step adds ("the last step leaves the row `2` (`2`, `12`, `6`) after the table's last row as written; …") or drops ("the table as written has the row `1` (`1`, `18`, `12`) after the last step's last row; …"). Each step shows the content as written with only what it names applied, so every step must name every cell whose value differs from that result, or the answer shows mid-run; no check catches that. The examples are the only inputs the check tries, and the page refuses numbers the build throws on, so add entries to `input.examples` for the edges (a zero, equal numbers, the bounds).
- **Code lines:** write the code as one fenced code block between the Stage's tags, and mark its lines with `lines`, by the number the page shows: from 1, or from the fence's `start` (` ```text start=0 ` makes the first line 0). Mark the line each step runs `reversed`, and only that one: the Stage draws it as a bar across the code and says "Linha L." after "Passo N de M.". Failures: "step 2 marks the line `9`, which the code doesn't have: it has lines 1 to 4" (or "… it has only line 1"), "step 1 has `lines`, but the Stage holds no code block: `lines` marks the lines of exactly one" (or "… holds 2 code blocks …"), and "step 3 marks the lines 2 and 3 `reversed`, but only the one running line is `reversed`".
- **Table rows:** a step's `body` replaces the rows of the Stage's one table, for a teste de mesa that gains a row per pass of a loop: one list of cell texts per row, one text per column. A Stage whose build uses `body` holds exactly one table, so a table of current values and a teste de mesa each take a Stage and a build of their own. Each row takes the look of the last row as written, and that step's `rows` and `cells` find rows among `body`'s, by their first cell, so give each row a first cell of its own (the pass's number). Give `body` on every step, since a step without it shows the rows as written, the whole result with `input`. With `input` the check fails a run that gives `body` on some steps and not on others, and `body: []` shows no rows. Give each step its own copy, `body.map((cells) => [...cells])`: a step keeps the lists it's given, so a later change to them reaches it too. Failures: "step 1 has `body`, but the Stage holds 2 tables: `body` rewrites the rows of exactly one" (or "… holds no table …"), "step 1 has `body`, but its table has no row as written for the new rows to copy: write one", "step 1 gives `body` a row of 2 cells (`1`, `18`), but the table has 3 columns: give every row one text per column", "step 2 marks the row `1`, which starts no row of this step's `body`", "step 3 changes a cell in the row `1`, which this step's `body` doesn't have", "step 4 has `body` that isn't a list of rows, each a list of texts" and, with `input`, "step 2 has no `body`, but this run's other steps rewrite the table's rows: give every step `body`, `[]` for no rows".
- **Say it for the ear:** `say` is read aloud, so write operators in words ("o resto de 48 por 18", "b não é zero"), as `COMPONENTS.md`'s Stage entry says.
- **Indexed reads may be `undefined`.** Builds are checked with Astro's `strictest` settings, `noUncheckedIndexedAccess` among them, so `weights[v]` or `queue[0]` is `T | undefined`: guard it or give a fallback with `??`. `pnpm look` builds and runs a Stage without type-checking its build, so shots that look right don't mean it passes: only `pnpm check` type-checks it.
- **Type a step as `Step`.** The Stage adds optional fields to `Step` as it grows, so a step built up field by field requires only the fields it fills, `Step & Required<Pick<Step, "parts" | "cells">>`, never `Required<Step>`, which breaks the build the day `Step` gains a field.
- **Marks act on some colour classes only.** `strong` and `dashed` change shapes with a `stroke-` class (and `strong` labels); `muted` greys the `-text` and `-accent` colours and unclassed labels; `reversed` turns `-surface` to ink and `-text`, `-accent` and unclassed labels to the ground. A vertex filled with `fill-muted` or `fill-tint`, or a label with its own `fill-` class, stays as drawn: draw what a build reverses as a `fill-surface stroke-text` shape with an unclassed label. `COMPONENTS.md`'s Stage entry lists them.
- **Runs:** after the build passes, the check runs `steps` on every option or example against the built page. Each failure names the option or example (`a = 48, b = 18`), the step and what's wrong, at the build file, and the page refuses the same runs: "with `B`, `steps` throws: …" (at the line that threw), "returns no steps", "returns more than 200 steps", "returns something that isn't a list of steps", "step 1 has a `say` that isn't text", "step 1 marks `A` in `parts` with `negrito`, which isn't a mark" (a cast can get past the types; the check still catches it), "step 3 has an empty `say`", "step 1 marks the part `D` `dashed`, which changes nothing in it: `dashed` acts on shapes with a `stroke-` class", "step 2 marks the part `C`, which the drawing doesn't have", "marks the row `B`, which starts no table row", "changes a cell in the column `Peso`, which heads no table", "names the row `A`, which starts more than one table row" (make each row's first cell and each header unique among the Stage's tables), and "`steps` didn't return within 5 seconds" (a loop that never ends).
- A Stage's own rules fail as `build`, under [Build failures](rules.md#build-failures): "Stage: there is no `x.build.ts` beside the entry", "give it `choose`, with a label and its options, or `input`, with its fields and examples", "give it only one of `choose` and `input`", "give `input` at least one example", "example 2 has `c`, which no field has", "example 2 has no `b`", "example 2 gives `a` 4.5, which isn't a whole number", "example 3 gives `b` 10000, outside 0 to 9999", "give `alt` with `figure`", "set `beside` only with `figure`". A text field's examples fail by the rule the page refuses typed text by, lengths counted in code points: "example 2 gives `w` \"abc\", whose c is outside the alphabet" (the first symbol outside), "example 3 gives `w` \"abab\", longer than 3", "example 4 gives `w` \"\", shorter than 1", "example 5 gives `w` \"bé\", which isn't in NFC" (an accent typed as its own code point: retype it), "example 7 gives `w` 5, which isn't text" (a number field given text keeps "which isn't a whole number"). So do a text field's props, and its examples aren't checked until they pass: "the field `t` has \"ab\" in its alphabet, which isn't one code point", "the field `t` has \"x\" more than once in its alphabet" (symbols compared in NFC), "the field `u` has `minLength` -1, which isn't a whole number of at least 0", "the field `v` has no `maxLength`", "the field `u` has `maxLength` 0, which isn't a whole number of at least 1", "the field `t` has `minLength` 3, above its `maxLength` 2", and a prop of the other kind, "the field `t` has `min`, which only a number field takes" (`min`, `max`) or "the field `n` has `alphabet`, which only a text field takes" (`alphabet`, `minLength`, `maxLength`).
- Builds aren't linted or formatted, and `CODING_STANDARDS.md` doesn't apply to them, but keep them short and plain: the next agent reads one to learn the job.

## Look

A `Stage` (kind `stage-choose`, or `stage-input` for typed input) is shot as written, then at every step of its first option, or of its first example, which Look runs by pressing Start on the fields as written:

- A Stage inside an `OpenQuestion`'s model answer is revealed and named as [Look](SKILL.md#look) says for any item there.
- Only the first option or example is shot; `pnpm check` runs the others. Put the one worth looking at first in `choose.options` or `input.examples`.
- Under the Stage, Look prints what it ran and its count of steps (`first option A, 5 steps`, `first example a = 48, b = 18, 5 steps`), or the refusal it got.
- Compare each step's shot with the step's line as well as the `alt`. A Stage without `figure` has no `alt`: Look prints its caption instead, so compare its shots with the caption and the step's line.
- Look asserts the current step and advancement after each action; a stuck control fails rather than producing repeated shots labelled as different steps.
